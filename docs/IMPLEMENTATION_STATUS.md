# Requirements Implementation Status

This matrix reconciles the historical high-level requirements (HLRs) and functional requirements
(FRs) with the repository implementation and available verification evidence as of August 10, 2026.
The historical requirements and prototype remain useful planning records, but source code, current
tests, API behavior, and physical-device evidence take precedence when they disagree. Phase D
mobile evidence below is current through August 10, 2026.

## Status Definitions

- **Implemented**: the required behavior exists across the necessary layers and has relevant
  automated or physical evidence.
- **Partially implemented**: a useful subset exists, but one or more material parts of the
  requirement or its acceptance criteria are absent.
- **Not implemented**: no working implementation of the requirement was found.
- **Out of current Android scope**: the requirement targets a platform or product scope not present
  in the current Android prototype.
- **Implemented but not physically verified**: source and automated evidence exist, but the
  end-to-end behavior has not yet been proven on the connected Android device.

Statuses are intentionally not treated as mutually exclusive. For example, a broad requirement may
be partially implemented and its implemented subset may still be awaiting physical verification.

  through a process-scoped `LOCKDIN_TEST_POSTGRES_ADMIN_URL` targeting a disposable container.
  Fresh bootstrap and an isolated dump/restore round trip also passed without touching the
  developer database or its volume.

- Phase D revalidation on August 8: Dart formatting and Flutter analysis passed; 52 Flutter tests,
  Android JVM tests, a debug APK build, and the backend suite (119 passed, 3 skipped) succeeded. An
  isolated Samsung SM-A528B run physically verified CA-trusted bootstrap, AppAuth registration and
  normal sign-in pages, `prompt=create`, Mailpit verification delivery, email verification, redirect
  to LockdIn, token exchange/introspection, protected `/api/v1/auth/session`, authenticated
  onboarding, and sign-out that remained cleared after an app-process restart. Successful refresh
  after a long-offline provider session, password-recovery delivery, and real SQLite v1 migration
  were not exercised successfully.
- Phase D account-deletion acceptance on August 10: the disposable identity completed fresh browser
  authentication, the backend returned `204`, the app reached **Welcome to LockdIn**, first-account
  creation became available, and the deleted credentials were rejected by Keycloak. Router
  transition and stale-binding defects found during the run were fixed. The full Flutter suite now
  passes 70 tests with clean analysis; the routed debug APK built and installed in place while the
  main SQLite database remained unchanged.
- Android Gradle/JUnit: 32 app tests passed on July 28, including exact-millisecond boundary,
  sub-minute remainder, and warning-copy tests.
- Strict MkDocs build: passed on August 3, 2026.
- Physical Android verification already covers UsageStats delayed-event recovery, back navigation,
  Picture-in-Picture, screen lock/unlock, offline usage recovery, rapid switching, Accessibility
  live tracking, the transition back to UsageStats, unique source IDs, and prevention of new
  cross-source overlaps. See [Testing and Current Evidence](TESTING.md).
- The July 26 read-only baseline found 1,835 raw usage rows, three enforcement-event rows, three
  rules, and zero duplicate `(profile_id, source_event_id)` groups. PostgreSQL was healthy and the
  health endpoint returned `200`.
- Android warning thresholds, warning-event logging, exact-limit soft intervention, dismissal, and
  backend evidence were physically verified on July 28. Per-app daily Rules CRUD was physically
  verified on July 31; all three tone profiles remain physical-device verification scope.
- A July 28 pre-merge recheck found both LockdIn containers running, PostgreSQL healthy, 3,692 raw
  usage rows, and 16 enforcement rows. The newest enforcement row remained the preserved `app_sync`
  duplicate; no later enforcement event had been created.
- The approved time policy now treats raw elapsed milliseconds as authoritative, floors only
  user-facing completed-minute totals, and evaluates warnings/intervention against exact time.
  Automated coverage confirms `299.9`, `300.0`, `300.1`, `315.4`, and `359.9` second behavior.
- On July 29, commit `60042dc` replaced the APK in place on the Samsung SM-A528B after a
  backend-only container rebuild. A UsageStats smoke check synchronized 8,946 milliseconds for
  Messages, returned `usedMinutes: 0`, retained the exact value in the native cache across a second
  refresh, and rendered `<1m used` in Rules. The exact-limit intervention boundaries were not
  repeated. Accessibility finished disabled and unbound; Usage Access remained allowed.
- Later on July 29, commit `050e42c` was installed in place after adding a Dashboard fallback for
  the restored Rules route. The user manually repeated the exact-limit intervention and confirmed
  that both the Rules top-left arrow and Android system Back returned to Dashboard instead of
  exiting. A read-only status check reported 318,793 milliseconds against the five-minute limit,
  correctly rendering `5m`, `106%`, and `over_limit`.
- On July 31, a regression APK exposed edit/delete access while a rule remained disabled. The user
  manually created, edited, and deleted a disabled TikTok rule while read-only checks confirmed
  its canonical package and stable rule ID, preservation of every unrelated enabled state, and
  retention of 176 historical TikTok minutes after deletion. The earlier unexplained Messages
  disable remains most plausibly an accidental interaction, but cannot be proven because its
  pre-restart request log is unavailable.
- On August 1, Dashboard, Trends, and Weekly Summary were physically reconciled with read-only API
  responses for the Samsung SM-A528B and the recorded time window. Friendly known-package names,
  exact category duration and `<1m` display, the 1,073-minute weekly total, hourly/category/top-app
  and peak-window analytics, navigation, responsive layout, and distinct analytics colors matched
  the physical UI. This evidence does not establish universal time-zone, midnight, or multi-device
  behavior, and location insights remain unimplemented.
- Weekly Summary goal/streak calculations currently treat missing dates as zero-usage successful
  days once any usage history exists. Synchronization or data-gap days can therefore inflate those
  two summaries; the semantic limitation remains unchanged.
- UsageStats synchronization runs on authenticated app open/resume and recovers at most three days.
  With Accessibility disabled, leaving LockdIn unopened longer can therefore leave older dates
  incomplete in the seven-day Weekly Summary. No current acceptance criterion requires a scheduled
  daily background analytics job; optional Accessibility live capture reduces this gap when the
  user enables it and keeps Usage Access granted.
